SongketMail arranges seven containerised services into a single, logically isolated deployment fabric. Every service runs inside the `songketmail` unprivileged user namespace, communicates over a dedicated bridge network (`songketmail-net`), and stores state in host directories owned by UID/GID `2001:2001`. No traffic enters the internal fabric without passing through BunkerWeb first, and no service exposes a port directly to the host unless it must accept inbound connections from the internet. The result is a defence-in-depth architecture where each component has the narrowest possible blast radius.

## Network and Pod Isolation

All components communicate over the virtual bridge network `songketmail-net` (subnet `10.89.0.0/16`). A dedicated pod (`songketmail_pod`) is defined at the pod level to declare the shared `UserNS` mapping for the fabric. The cluster-prefix convention — applied to the pod name, network name, and every container name — means you can safely run multiple independent fabrics (for example, staging and production) on the same hypervisor without risking port or network name collisions.

```ini
[Network]
NetworkName=songketmail-net
Subnet=10.89.0.0/16
Internal=false
```

The pod declares `UserNS=keep-id:uid=2001,gid=2001` once at the pod level. This ensures a consistent, predictable UID mapping across every service without repeating the directive in each individual `.container` file.

<Note>
  Only `songketmail-proxy` binds host ports (80, 443, 25, 587, 993). All other services communicate exclusively over `songketmail-net` and are invisible to the host network interface. This is intentional — never expose internal service ports directly to the host on a production node.
</Note>

## Storage Path Structure

All host-side persistence lives under a single, predictable root:

```text
/var/srv/songketmail/
├── bunkerweb/data/          # BunkerWeb WAF runtime data
├── nginx/conf/              # NGINX upstream configuration
├── certs/                   # TLS certificates
├── postfix/config/          # Postfix main.cf and virtual tables
├── postfix/spool/           # Mail queue spool
├── dovecot/config/          # Dovecot configuration
├── dovecot/indexes/         # Mailbox index files
├── dovecot/cache/           # Dovecot cache
├── postgres/data/           # PostgreSQL data directory
├── rustfs/data/             # RustFS object storage volumes
├── roundcube/config/        # Roundcube PHP configuration
├── roundcube/db/            # Roundcube SQLite session store
├── rspamd/config/           # Rspamd local overrides
└── rspamd/data/             # Rspamd Bayes and statistics data
```

Every directory is created by the Ansible playbook and assigned `2001:2001` ownership before any container starts. Because `UserNS=keep-id:uid=2001,gid=2001` aligns the container-internal UID to the host UID, files written by a running container appear on the host with correct ownership — no `sudo`, no `chown`, no mystery `nobody:nogroup` entries.

<Tip>
  To inspect or back up any service's data, log in as the `songketmail` user and navigate directly to `/var/srv/songketmail/{service}/`. You own every file there without needing elevated privileges.
</Tip>
