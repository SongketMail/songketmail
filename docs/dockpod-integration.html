📊 DockPod Integration: Unprivileged Podman & Agentic Management

Control Plane MCP Server Enabled Unprivileged Socket

1. Executive Summary

This deep research document explores the integration of DockPod (available at guide.dockpod.io) within the SongketMail ecosystem. SongketMail is an enterprise-grade, rootless, unprivileged email server fabric orchestrated via Podman 5+ and systemd Quadlets.

Our primary objective is to evaluate DockPod as a lightweight, zero-dependency control plane to manage, monitor, and troubleshoot all Podman containers within this project. Additionally, we analyze how DockPod's native Model Context Protocol (MCP) server can be leveraged by AI agents—such as Google Jules—to perform real-time autonomous container operations, log monitoring, and automated deployments securely.

⚡ 2. DockPod Overview & Core Capabilities

DockPod is a single, compiled Go binary with less than a 30MB RAM footprint, containing an embedded React web UI and SQLite.

  • • Dual-Engine Auto-Detection: Auto-detects Docker and Podman sockets, making it highly versatile.
  • • Embedded Console & Live Logs: Streams log outputs via WebSockets and launches full container exec terminals.
  • • Built-In MCP Server: Provides an out-of-the-box Model Context Protocol (MCP) server on port 8090, granting LLM agents robust troubleshooting tools.

🏗️ 3. Architectural Alignment with the Persistence Trinity

DockPod executes perfectly as an unprivileged, user-level systemd service under the target songket user session (UID 2001). By mounting the user-level rootless socket /run/user/2001/podman/podman.sock, DockPod achieves complete visibility over SongketMail containers without requiring any root privileges or elevated host permissions.

🔒 Storage Sovereignty Maintained

DockPod requires zero write privileges to host mail directories (under /var/srv/songketmail/). It interacts strictly with the Podman daemon over the UNIX socket, preventing un-audited file mutations.

4. Rootless Podman Socket Activation

By default, Podman's rootless API socket is inactive. It must be enabled under the target user's systemd context: 

# Switch to songket user shell environment
export XDG_RUNTIME_DIR="/run/user/2001"
export DBUS_SESSION_BUS_ADDRESS="unix:path=/run/user/2001/bus"

# Enable and start user socket
systemctl --user enable --now podman.socket

# Export the socket for DockPod configuration
export DOCKPOD_SOCKET="/run/user/2001/podman/podman.sock"

5. Agentic Control via Model Context Protocol (MCP)

For AI agents like Google Jules, the Model Context Protocol (MCP) server acts as a structured API gateway. Instead of running fragile shell scripts to extract log lines or diagnose failures, Jules can fetch real-time container metrics, list active networks, or trigger service updates through standardized JSON-RPC schemas.

Diagnostic Tools
  • list_containers
  • get_container_logs
  • get_system_info
Control Actions
  • restart_container
  • pull_image
  • set_deploy_app_resources

6. Operational Boundaries & Recommendations

Feature Manual Quadlets DockPod Mode Decision
Orchestration Git-tracked Quadlet files Ad-hoc Compose / Git deploys Keep Quadlets as single source of truth.
Ingress Proxy Nginx + PROXY protocol Embedded Traefik Proxy Disable Traefik. Keep Nginx to preserve client IP.
Scope Full lifecycle deploys Web dashboard log streams Utilise DockPod strictly for read-only diagnosis.

💡 Strategic Integration Recommendation

We recommend deploying DockPod as a user-level background systemd service for the unprivileged songket user session. The panel's role should be locked down to read-only container monitoring, metrics plotting, and log inspections, while its Model Context Protocol (MCP) server should be configured to grant secure, schema-validated operational diagnostics directly to Google Jules. This gives the developers an exceptional real-time view of the mail fabric without compromising the security of rootless container sandboxing.
